`.github/workflows/demos.yml` now publishes both, with a landing page, to GitHub Pages on
every push to `main` (D035): one manual Pages enable plus a push away from live.

**Every `src/` file `ARCHITECTURE.md` asks for now exists, and both of its front ends do
too, in the shape the platform allows rather than the shape §11 sketches.** `web/` is
written and documented in [07-web-dashboard](../07-web-dashboard/00-overview.md), `firetv/`
in [08-fire-tv-overlay](../08-fire-tv-overlay/00-overview.md) — neither as React, because
`react` cannot be installed in this environment (D029), and the overlay's sanctioned Vega
surface is a WebView anyway (D021, D034). Still missing and required by the specs:

| Missing path | Required by |

| `firetv/App.tsx`, `firetv/components/Overlay.tsx` | `ARCHITECTURE.md` §11 — the React Native Kepler shell; cannot compile or run here, and the WebView hosting path makes it optional rather than blocking. See [08-fire-tv-overlay](../08-fire-tv-overlay/00-overview.md) |
| `test/handlers.test.ts` | `ARCHITECTURE.md` §11 — superseded by 16 focused suites; a single combined file would be a regression, not a gap |

`template.yaml` declares **seven** Lambda functions across five source files
(`webhookHandler.handler`, `snapshotFetcher.handler`, `overlayPusher.handler`,
`overlayPusher.onConnect`, `overlayPusher.onDisconnect`, `eventQuery.handler`,
`dailySummary.handler`), three DynamoDB tables, two SQS queues with dead-letter queues, an
HTTP API carrying both the webhook and `GET /events/today`, a WebSocket API with
`$connect` and `$disconnect` routes, an EventBridge schedule for the daily summary, four log
groups, and the snapshot bucket with its policy — **plus 25 resources in total**, two of
which are conditional on a notification address being supplied. It has **never been
deployed or validated**. No AWS account and no SAM CLI are available here, so it is checked
only for YAML well-formedness — parsed with a duplicate-key detector, which is how two
pre-existing duplicate keys in `QueryApiKey` were found — and for consistency with the build
output. All seven `Handler` paths were asserted to resolve to real function exports in
`dist/`, by requiring the built bundles, and that is as far as the verification goes.

**One** thing `ARCHITECTURE.md` requires is still missing from the code, and it is not
fixable by writing more of it:

- **The events table is read and written by a single homeowner's key.** `GET /events/today`
  queries the `date` partition and the daily summary reads and writes the same one, but
  there is no per-account separation anywhere: one table, one static `X-Query-Key`, one
  homeowner. That is a deployment blocker for anything multi-user, recorded as D022.

**A third recorded gap closed this phase.** Device-name resolution: `ringClient.getDevice()`
existed and was never called, so every stored event read "at the door" in the FR11 fallback
and the §3.6 context could not say which camera it was describing. The describe stage now
resolves it, *before* building the sentence, and persists it — D031.

**Two previously recorded gaps are now closed.** The 90-day TTL on the events table was
declared in `template.yaml` and never written, so events were retained forever —
`putEvent` and `putSummary` now set `expires_at` from the row's own date partition (D028).
And §6's Bedrock cost-runaway detection is now declared as `CostAlarmBedrockBudget`, an AWS
Budget filtered to the Bedrock service, rather than the CloudWatch alarm the spec named
(D027). Neither has been created or observed: no account, no SAM CLI.

The 1-hour pre-signed URL that §6 requires **is** implemented, in the delivery path
rather than a query path: `src/lib/overlayPush.ts` signs each snapshot key with
`PRESIGNED_URL_TTL_SECONDS = 3600` and sends the signed URL in the §3.4 payload. What
is still absent is any read path that would need to sign on the owner's behalf.

`.env.example`, `package.json`, `src/lib/signatureVerifier.ts`, and
`src/lib/dynamoClient.ts` were on this list until their phases created them; the
contract's self-invalidating declarations flagged each the moment it appeared, which is
how this table stayed correct instead of going stale.

**The chain now reaches the wire, the events are readable, and the day is summarised.**
Ingress → queue → snapshot → Bedrock → WebSocket is wired and tested against fakes,
`GET /events/today` returns a day's events with pre-signed snapshot URLs, and the daily
summary reads a UTC partition and writes one row back into it. **Every backend stage
`ARCHITECTURE.md` plans is written.**

**A homeowner can now see the day, and a television can show the moment.** `web/` reads
`GET /events/today` and renders the day's events, their snapshots, and the §3.6 summary. It
was **rendered in a real browser for the first time on 2026-10-04**: the demo page
(`web/dist/demo.html`, fixture data through the production rendering path — D032) and the
live page, whose no-backend state renders the unmistakable error panel rather than a quiet
day, and whose controls were exercised. `firetv/` receives the §3.4 push over the Overlay
WebSocket and shows one event full-screen with the 15-second auto-dismiss (FR14) and a
D-pad-reachable dismiss button (FR13) — also rendered and exercised in a real browser that
day, through its fixture demo (D034). What still does not exist is anything running on an
actual television, or the picture-in-picture §3.4 originally specified — not implementable
on Vega OS at all (D021). `description_source` on each event distinguishes a model-written
sentence from an FR11 fallback.

No event has ever been produced by a live Ring delivery, and the FR6 8-second target is
unmeasured across three queue hops.
